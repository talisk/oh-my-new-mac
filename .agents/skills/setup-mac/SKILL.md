# setup-mac

在仓库根目录读取 `AGENTS.md`，遵循 `docs/workflow.md`。核心链路是：**盘点 → 需求确认 → 具体变更计划 → 按已确认范围执行 → 验证和交接**。不要运行全量安装器，不把“新 Mac”当作空白机器。

## 1. 先盘点，再提问

确认操作的是用户要配置的那台 macOS，而非云端/Linux 容器；查看 OS、架构、Rosetta、shell、真实配置入口、工具位置和安装来源。按 `docs/workflow.md` 控制读取范围。先不安装、不修改系统或用户配置。

若 `.local/` 有此前报告，先核对本机现状，再复用已确认选择；发现漂移只询问受影响项。只把备份/凭据文件的存在及必要的非敏感设置用于判断，不输出完整秘密。

## 2. 用 AskUserQuestions 串联需求

读取 [问题设计](references/questions.md)。先告知盘点结论，再按相关性逐轮提问，而非一次抛出所有工具。

- 宿主提供 `AskUserQuestions` 时优先使用它，读取真实 schema 后调用；这不是要求安装一个同名 CLI 或 MCP。
- 名称不同可用同等工具，如 `AskUserQuestion` 或 `request_user_input`。必须遵循该工具的模式、题数、多选和权限限制，不能假设当前环境一定有工具。
- 工具不可用时用简短普通对话提问并等待；用户已给出的选择直接复用。不要输出虚构的 tool call，不为提问改变宿主安全设置。
- 选项用于确认需要什么。涉及宿主审批、sudo、登录、付费或新的外部动作，仍走宿主指定的权限流程；需求问卷不能授予不存在的权限。
- 用户不回复时继续只读盘点和整理建议，不把沉默当作允许覆盖、安装、升级或启用定时任务。

## 3. 给出可审阅的计划

按组件展示：当前来源/版本、保留/新增/迁移/跳过、命令依据、要改的文件、备份与回滚、是否需要用户登录。标明额外依赖、可能的收费或公开数据行为。

新机器可建议最小开发基础；已有机器默认保留可用工具，说明本仓库推荐方案与当前方案的差异。没有 GitHub 原项目或官方安装证据的项目标记待核验（目前包括 traex），不猜测执行。

确认计划时把真实新增与修改项目说清楚。如果用户之前已明确授权对应计划，就直接执行，不重复索要同一授权。若用户只选择“给建议/仅检查”，到建议阶段结束，不动环境。

## 4. 执行所选模块

只读用户选择的文档：

- 基础/语言环境：`docs/development.md`。
- AI CLI、手动/自动升级：`docs/ai-cli-upgrade.md`。
- 文件浏览、Markdown、音乐、电台、搜索、部署或图床工具：`docs/terminal-cheatsheet.md`。
- 后台删除：`docs/rm-async.md`；安装工具不授权删除现有文件。
- 来源与当前安装依据：`docs/sources.md`；原始附件在 `docs/imported/`，仅为历史资料。

执行前重新核验所选项目的当前官方方法及平台支持。按依赖顺序逐项安装，记录命令、退出码和配置差异；失败隔离到相应组件。不要用已存在的二进制掩盖刚刚失败的安装，也不要因为 PATH 冲突就卸载另一个版本。

补写 shell 配置时先备份真实文件、比较内容，再更新唯一标记块。相同状态不重复写。更换管理器、清理重复渠道、迁移 Kimi 等操作只在明确选择后执行。

## 5. 验证和交接

按 `docs/validation.md` 分层验收；至少在新的交互式 shell 中验证所选命令及来源。后台删除必须通过有控制终端的 PTY 用例，不能只跑管道测试。

不为证明安装成功而发布站点、上传图片、生成计费请求、删除真实缓存或导出令牌。认证/音频/GUI/launchd 没有实测就明确列为待验证。

参照 `templates/setup-report.md` 在 `.local/` 记录已完成、保留、跳过、失败、待用户操作、备份和回滚方法。最后给出简短使用说明和未完成项。不要将本机报告、日志或秘密提交 Git。
