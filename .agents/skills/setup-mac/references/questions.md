# 需求问答设计

先读 `docs/README.md` 和五个分类 README，以其工具列表生成本次选项。不要在本文件再复制一份静态全量名单。按 `docs/guides/selection-and-conflicts.md` 解释范围和冲突策略。

## 先展示实际目录

盘点结论简短说明已装环境，然后在问答前按“基础环境 / AI tools / 实用脚本 / CLI 工具 / GUI 应用”分组展示**各组内全部工具名称**，附已装/缺失和重要来源限制。CLI/Desktop 必须标明，不能把 Cursor 两个条目合并成一个含糊选项。

若宿主多选 UI 能容纳，分组展示可选工具；不支持分组/长列表时先用普通消息列出目录，再用工具确认范围。不要因为单轮最多 3 个问题就省掉某类工具，或把一堆工具塞成不可辨认的一个选项。

## 第一轮：范围入口

未得到范围时，用真实 `AskUserQuestions` / `AskUserQuestion` 的 schema 提问。推荐语义选项：

| 选项 | 结果 |
|---|---|
| 按分类 / 名单选择 | 下一轮收集分类、白名单或黑名单；冲突默认询问 |
| 一键全选，自动处理冲突 | all + auto + allow-required；目录是完整范围，常规配置冲突由 agent 决定，无需再确认 |
| 仅检查与建议 | 不修改用户环境；给出现状和推荐配置 |

用户也可直接回答“全选，但冲突问我”，得到 all + ask。工具只支持固定数量选项时保留上述入口，其他偏好用工具自由输入能力或后续简短一轮收集，不编造多选字段。

明确告知：全选允许补装必要依赖，保留兼容的已有工具，无法无损解决的项会跳过；不包括定时升级、永久唤醒、登录同步或付费服务。用户选择了“一键全选”就进入计划与执行，不再逐分类选一次、不再要求“确认无误后开始”。

## 分类 / 名单分支

仅当用户选了自定义范围且未提供名单时询问：

| 问题 | 选择或输入方式 |
|---|---|
| 如何指定范围 | 按分类/工具多选；白名单（只安装这些）；黑名单（这些不装，其余全部） |
| 工具列表 | 从分类 README 展开；可多选、粘贴名称或工具 ID，允许组合分类和排除项 |
| 冲突处理 | 发现冲突询问（默认） / agent 自行保留、合并、修复，无法安全处理则跳过 |

白名单严格解释为“只安装用户提到的”。明确展示缺失依赖；用户可选“允许必要依赖”扩大范围。没有选择就保持 strict，尤其 auto 不能把 Homebrew/Node/编译库偷偷加进去。只给黑名单时以全目录为基集；分类黑名单排除整类。

示例回答及应有解释：

- “只装 brew、nvm、node、pyenv、python、uv” → 规范化为这六项，不顺带装 AI/GUI。若 CLT 缺失，属于需要说明的额外依赖。
- “基础环境和 AI 全部，不要 grok 和 Gemini，冲突别问” → 展开两个分类减去排除项，auto；不处理未选 GUI。
- “全选，排除 Cursor Desktop 和防休眠工具” → 排除 cursor-desktop、caffeine、amphetamine；Cursor CLI 仍在范围。
- “只要 Cursor” → 无分类上下文时 ask 消歧；auto 模式则记录该项歧义并跳过，不代选两个。

不要因为某个工具来源待确认或平台不支持，把整轮问答卡住。用户纠正选择时只更新相关集合，不重新询问已确定项。

## 可选偏好和实际冲突

项目版本约束优先从用户明确指定的项目配置读取；不要广扫其他项目。已有明确约束不再问。需要选择时可问 Node/Python 目标版本、shell 集成及维护方式；auto 缺省使用工具页的安全默认值，无需补一轮偏好问题。

`ask` 只问实际发现的冲突，说明现状、推荐方案、影响及回滚。例如“Codex npm/Brew 双装，目前 npm 生效；建议保留 npm，是否需要改渠道？”已知冲突可集中一轮，避免每个命令一个确认。

`auto` 不发送这类配置裁决问题；诊断后自行处理并记录理由。新依赖越过黑名单、不同产品替代、不可回滚覆盖都不是可自行接受的普通冲突，无法在既有授权范围内完成就跳过该项。

定时维护只有明确选择后才收集工具范围、频率、时间与非交互更新策略。全选只生成手动维护工具，不默认启用 launchd；不套用附件的个人时间/label。

## 计划、无回复与宿主限制

展示具体变更和依赖后，有明确安装指令就继续；无授权的纯建议请求停在建议。不能把用户没有回答视为全选或 auto。已授权部分可以继续，缺失回答只影响对应未确定部分。

需求工具不可用时使用普通对话，保留相同语义。工具的审批禁用规则仍有效；系统密码、账号认证、付费、协议等走宿主的正式机制，不能把配置问卷当作权限提升。auto 下不能完成的用户专属操作记录待办，继续独立项。
