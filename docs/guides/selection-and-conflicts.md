# 选择范围与冲突处理

这是 README、AGENTS 与 setup-mac 共用的决策规则。**安装范围与冲突策略分开记录**：全选不必然代表自动处理，白名单也可以要求不询问。

## 选择模型

先读取 [总目录](../README.md) 及五个分类 README 的工具 ID/别名。保存用户原话、规范化结果和本次清单快照，不把下面的字段当必须实现的安装程序 schema：

| 字段 | 含义 / 默认值 |
|---|---|
| 动作 | 检查 / 配置 / 继续；以用户实际指令为准 |
| 范围 | all / 分类集合 / 白名单；只给黑名单且明确要求配置时，基集是 all |
| 排除集合 | 黑名单；可写工具、分类、明确的发行渠道 |
| 冲突策略 | `ask` 默认 / `auto` 用户授权自行处理 |
| 依赖策略 | 白名单默认为 `strict`；all/分类默认 `allow-required`；用户可覆盖 |
| 附加偏好 | 版本/渠道要求、shell 集成、定时维护等；不推断未选的外部行为 |

最终目标 = 展开的基集减去排除集合。白名单与黑名单重叠时黑名单优先；后续明确更正可修改该集合，不能让一段模糊推荐覆盖先前排除。排除只表示本次不安装/修改，不是卸载现有工具的指令。

- “全部装，冲突你解决，不要再问” → all + auto + allow-required。展示具体清单/方案后继续执行，不追加一个重复的“是否继续”。
- “全部装” → all + ask + allow-required。只问实际冲突和确有缺失的关键偏好，不逐工具重复确认。
- “只装 uv、ripgrep；别问冲突” → 白名单 + auto + strict。没有授权新装 Homebrew，就不能把它作为便捷手段暗中添加。
- “除了 GUI 和 grok 都装” → all 减去 gui-apps 分类与 grok，冲突仍为 ask。
- “只装 yazi，可安装必要依赖，不装 ffmpeg” → 白名单 + allow-required + 黑名单 ffmpeg。可装未被排除的真正依赖，不能给 yazi 配上被排除的预览组件。

## 名称和依赖不能偷换

按分类上下文消歧。`codex` 指 CLI，`codex-desktop` 指 App；明确在 GUI 类选择 Codex 就映射桌面项。`Cursor` 未带上下文可能是 CLI 或 Desktop；`ask` 时询问，`auto` 时跳过这一歧义项并说明，不自动安装两者。同名但发行方不同的 Otty、Caffeine、Surge 依工具页核验。

`strict` 表示只对所列组件执行安装/修改。先利用已有合适依赖；尚缺的运行时、包管理器、编译库和包依赖都列出来，不作为隐藏安装。`ask` 可一次性询问是否扩大到明确的必要依赖；`auto` 优先选择无需增装未选组件的官方渠道，否则将该项标为缺依赖并继续。

`allow-required` 允许已选组件运行所必需的依赖，但先在计划中列出。不要把推荐插件、另一套版本管理器或可选预览功能混为必要依赖。Brew 的当前依赖图、npm engines、安装器会写入的组件都属于检查范围；若安装必然会新增/改动黑名单组件，换经核实且不冲突的渠道，或者跳过父项。不能用“包管理器自动安装”绕过排除。

用户说“不安装 Node”且现有 Node 能用时，允许只读使用已有 Node，不升级/重配它；若用户明确“不使用 Node”也禁止把它作为依赖。版本不兼容时不能在黑名单外私自升级。

## 冲突默认询问，也可全程自行解决

`ask`：先完成诊断，提出具体建议和影响；同一批已知冲突可集中询问。已授权的决定不再问。只询问需要选择的差异，不把正常补装、可回滚的无冲突加载块反复当审批。

`auto`：用户授权 agent 为所选项目自行作出常规配置决定。保持已确认目标，按下表处理；没有安全方案就跳过该项，不回头要求用户逐项裁决。

| 冲突 | 自动处理方式 |
|---|---|
| 已有兼容且来源可信的工具 | 保留并验收；不为统一包管理器重新安装 |
| 多渠道、多架构 | 保留当前合适的生效渠道；不批量卸载、强制 link 或自动切 Rosetta |
| PATH / shell 初始化重复 | 定位实际入口、备份后合并或去掉确定的重复加载；保留用户其他内容与框架 |
| nvm 与 fnm/mise 同时存在 | 保持一个现有可用管理器生效；若没有明确迁移目标，nvm 可安装但不抢默认，报告集成未启用 |
| system/nvm Node 不一致 | 按 [Node 指南](../base/node.md) 先找满足约束的共同精确版本；不强制升级系统包或破坏其他项目 |
| pyenv 与 uv 双重管理 Python | 按 [uv 指南](../base/uv.md) 新环境用 pyenv 解释器、uv 管环境；保留既有 uv-managed/conda 项目 |
| 自定义同名函数、按键或设置 | 能保留语义才合并；否则保留原配置并跳过冲突集成，二进制可独立完成 |
| 同名 App 或新产品替代旧产品 | 先核验发行方；保留原来匹配的产品，不把替代品伪装为所选工具 |
| 可回滚修复仍无法恢复功能 | 回退本次差异，标记失败/跳过，继续独立项目 |

“自行解决”不是默认跳过所有差异：能够安全补装、合并、修复的要实际完成。跳过需写明证据、已尝试的安全路径及未满足的目标。不得把“保留旧版本”写成“已升级”，或把两个 Node 入口能运行写成“版本完全统一”。

## 自动模式的边界

全选/auto 不授权删除用户数据、清空配置、卸载原工具、关闭安全机制、强制覆盖、发布/上传内容、开通付费服务或启用周期任务。不会自动接受新协议、代输入密码或绕过宿主审批。请求的安装本身及可回滚配置改动可按已有授权完成，不为普通冲突另问。

需要系统/账号交互时，提交宿主正式审批/登录流程；若当前不能完成，记为“待用户操作”并继续其他项目。这个结果与“等待用户选择配置方案”不同。不要因 auto 而切到 bypass/YOLO，也不要说“全选成功”掩盖这些缺口。

定时 CLI 升级、开机启动、防休眠会话、默认浏览器/编辑器、云同步、第三方扩展均不是全选的默认动作。可在首次需求阶段附加选择；没有选择就保持现状，新机保持未启用。
